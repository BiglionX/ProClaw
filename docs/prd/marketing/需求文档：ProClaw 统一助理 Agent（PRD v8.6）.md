### 1. 背景与目标

#### 1.1 背景
- 当前桌面端右下角的浮动 AI 聊天窗口定位为通用「ProClaw 经营智能体」，身份模糊、缺乏人格化特征，且职责边界不清晰。
- 过去系统同时存在「商务秘书」（小如，负责数据查询/简报）与「CEO Agent」（负责决策/任务分派），两个 Agent 拥有独立的入口、记忆和人格，导致老板心智负担重，决策类请求还需在秘书和 CEO 之间来回跳转。
- 本轮升级将两者合并为**统一助理**：保留「小如」的人格化秘书形象，内化 CEO Agent 的决策建议、任务分派、目标管理与报告能力。决策类请求不再被生硬拒绝，而是内部路由为「生成建议 → 确认 → 写入决策日志/分派任务」。
- 参考豆包等 AI 助手的头像个性化设计，用户期望能自定义助理的**名称、头像**，形成情感连接。
- 语音交流是未来必然趋势，需在设计阶段预留接口和交互入口。

#### 1.2 产品定位：统一助理

```
┌─────────────────────────────────────────────────────────┐
│                     Boss（老板）                          │
│                                                         │
│           ┌──────────────────────────┐                  │
│           │     统一助理（小如）        │                  │
│           │   秘书人格 + CEO 能力内化   │                  │
│           │                          │                  │
│           │  ✅ 读数据 · 分析 · 呈报    │                  │
│           │  ✅ 决策建议 · 确认卡片     │                  │
│           │  ✅ 任务分派 · 进度跟进     │                  │
│           │  ✅ 目标记录 · 经营报告     │                  │
│           └───────────┬──────────────┘                  │
│                       │                                 │
│                       ▼                                 │
│   ┌──────────────────────────────────────────────┐      │
│   │          全系统数据（产品/库存/销售/财务...）      │      │
│   │   项目上下文协议（PCP） / 决策日志 / 任务表        │      │
│   │          子 Agent 团队（财务/营销/运营...）        │      │
│   └──────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────┘
```

| 维度 | 统一助理（小如） |
|------|-----------------|
| **核心职责** | 数据查询、统计分析、情报呈报、异常提醒、**决策建议**、**任务分派**、**目标管理**、**经营报告** |
| **数据权限** | 全系统只读业务数据；通过确认流程间接驱动 PCP/任务/决策日志写入 |
| **决策能力** | 不替老板拍板；识别决策意图后生成建议卡片，经老板确认再执行 |
| **交互频率** | 高频——随时响应老板各类经营相关请求 |
| **学习目标** | 同时学习「老板关注什么数据」（BAP）和「老板如何做决策」（决策偏好） |
| **上下文存储** | 老板画像 = BAP（关注 KPI） + CEO 偏好（风险/预算/风格） + PCP 目标 + 决策日志 |
| **常驻位置** | 桌面端所有页面右下角（FloatingAgentChat）；移动端联系人列表 / 浮动入口 |

> **一句话总结**：小如从「只看数据的秘书」升级为老板的「全能助理」——既能看清现状，也能提出方案、分派任务、记录目标，但所有经营动作都需老板确认。

#### 1.3 目标
- **身份重塑**：将右下角浮动 AI 助手重新定位为 **「统一助理」**（Unified Assistant），以「小如」为默认名称与形象，作为 ProClaw 的**内置 Agent**，出厂即带，无需从市场安装。默认形象为**女性**。
- **能力合并**：在保留秘书人格化交互的基础上，内化 CEO Agent 的决策建议、任务分派、目标管理、经营报告能力，消除双 Agent 入口和记忆割裂。
- **意图路由**：通过规则化意图分类（查询 / 决策 / 任务 / 上下文 / 报告）自动识别老板请求类型，决策类请求进入确认流程而非简单拒绝。
- **统一记忆**：建立「老板画像」，融合 BAP（关注 KPI）、CEO 偏好（风险/预算/风格）、PCP 活跃目标、决策统计，让助理越用越懂老板。
- **人格化定制**：支持用户右键设置助理的**名称**和**头像**，打造专属感。
- **语音预留**：在 UI 和架构层面为未来的语音对话功能预留空间。

### 2. 用户故事

#### 2.1 人格化交互
- **作为** 商户老板，我打开 ProClaw 桌面端，右下角出现一个可爱的女孩秘书头像。我右键点击，给她取名「小鹿」，换上一个干练的商务女性头像。从此每天和她对话，就像和自己的专属秘书交流。
- **作为** 新用户，我第一次打开 ProClaw，右下角出现一位干练的女孩秘书，默认名为「小如」。她主动打招呼：「老板，有啥交代？^-^」

#### 2.2 数据查询与分析
- **作为** 老板，我问秘书：「最近一周销量最好的前 5 个产品是什么？」秘书瞬间拉出排行榜，并附注「其中产品A已经连续 3 周位居榜首，建议关注补货节奏」。
- **作为** 老板，我对秘书说：「对比一下本月和上月的毛利率。」秘书生成对比报表，主动标注出毛利率下降最多的 3 个品类，并提示「如需深入分析，我可以让财务 Agent 出一份专项报告」。
- **作为** 老板，我每天早晨打开 ProClaw，秘书自动推送一条**今日经营简报**：「老板早上好！截至昨天：今日待处理订单 12 笔，库存预警 3 项，昨日营收 ¥8,520，比前天 +5.2%。祝您今天顺利！」

#### 2.3 越用越懂老板
- **作为** 老板，我经常问库存和毛利率，很少问营销数据。几周后秘书的简报自动把「库存预警」和「毛利概览」放在最前面，营销数据则精简为一句话。
- **作为** 老板，我曾让秘书「每周五下午提醒我审审批预算」。从此秘书每周五准点提醒，并附上本周预算执行摘要。
- **作为** 老板，我连续多次在问完销售数据后追问「退货率」。秘书学会了：以后报销售数据时，自动附带退货率。

#### 2.4 决策支持而非替代
- **作为** 老板，我问秘书：「库存不足了，帮我自动下单补货吧。」统一助理识别为采购决策，生成建议卡片：「检测到采购决策请求，建议执行补货。风险等级：中，资金影响：较大。请在弹窗中确认。」我点击「确认执行」后，助理将该决策记入日志，并提示我可以到采购模块执行下单。
- **作为** 老板，我问秘书：「你觉得我应该开除哪个员工？」统一助理回应：「老板，人事决策我无法替您拍板。我可以帮您拉取团队绩效数据，并生成一份人事决策建议供您确认。」

### 3. 功能设计

#### 3.1 身份定位

| 属性 | 说明 |
|------|------|
| **Agent 类型** | 内置 Agent（Built-in），非市场安装 |
| **Agent ID** | `builtin:secretary`（历史 ID 不变，保持兼容） |
| **显示名称** | 默认为「小如」，用户可自定义 |
| **默认头像** | ProClaw 品牌默认秘书形象（**女性**，商务风格） |
| **性别** | 女（默认，不可切换） |
| **数据权限** | 全系统只读业务数据；通过确认流程间接写入 PCP、任务、决策日志 |
| **决策权限** | 不替老板拍板；识别决策意图后生成建议卡片，经确认后执行 |
| **系统角色 prompt** | 「你是『小如』，ProClaw 系统的全能助理 AI，融合了商务秘书与 CEO 主控官的能力。你是老板的贴身助理和数据参谋，专业、细致、高效；能提出经营决策建议、管理目标、分派任务、生成报告；始终保持专业、耐心，不确定时坦诚说明，涉及决策/任务时引导老板确认。」 |
| **常驻位置** | 桌面端所有页面右下角（FloatingAgentChat 组件位置）；移动端联系人列表 / 浮动入口 |

#### 3.2 核心能力矩阵

| 能力 | 说明 | 示例 |
|------|------|------|
| **数据查询** | 支持自然语言查询全系统数据 | 「上月销售额」「库存<10的产品」「供应商A的采购记录」 |
| **统计分析** | 排行、对比、趋势、占比 | 「近3月销售趋势图」「品类毛利占比」「环比增长率」 |
| **异常预警** | 主动监测并提醒异常指标 | 「产品A库存低于安全线」「今日退货率异常升高」 |
| **定时简报** | 按老板偏好推送每日/每周经营摘要 | 每日早安简报、周五周报、月初月度对比 |
| **关联洞察** | 发现数据间的隐含关联 | 「销量上升的同时退货率也在上升，可能与某批次质量有关」 |
| **决策建议** | 识别采购/定价/人事/营销/财务类请求，生成决策确认卡片 | 「帮我下采购单」→ 弹出确认卡片，记录决策日志 |
| **任务分派** | 将老板的意图拆解为任务并分派给合适的子 Agent | 「给营销团队分派一个活动方案任务」→ 写入 `ceo_tasks` 并通知子 Agent |
| **目标记录** | 将老板的口头目标记录到 PCP | 「记录目标：下季度销售额翻倍」→ 写入 `project_context` |
| **经营报告** | 生成日报/周报/项目进展报告 | 「生成本周经营报告」→ 汇总 PCP + 任务 + 业务数据 |
| **记忆融合** | 综合 BAP、CEO 偏好、PCP 目标、决策统计生成老板画像 | 回答时优先提及老板常关注的数据和决策风格 |

> **能力边界**：统一助理可主动提出决策建议、分派任务、记录目标，但**不替老板拍板**。所有涉及经营动作的请求需经老板确认（确认卡片）后方可写入日志或分派任务。

#### 3.3 老板关注配置（Boss Attention Profile, BAP）

秘书的核心差异化能力——**记住老板关心什么，并越来越精准地服务**。

##### 3.3.1 BAP 是什么

BAP 是统一助理「老板画像」的一部分，记录老板的数据偏好，存储在 SQLite 中（与 PCP 共同构成统一记忆层）：

```sql
CREATE TABLE secretary_bap (
  id TEXT PRIMARY KEY,
  profile_type TEXT NOT NULL,  -- 'kpi_preference', 'time_routine', 'alert_threshold', 'focus_area', 'custom_rule'
  key TEXT NOT NULL,
  value JSON NOT NULL,
  confidence REAL DEFAULT 0.5, -- 置信度（0-1），越高越确定是老板的稳定偏好
  source TEXT DEFAULT 'observed', -- 'observed'(观察习得) / 'explicit'(老板明确设置) / 'inferred'(推理)
  last_matched_at INTEGER,
  created_at INTEGER DEFAULT (unixepoch()),
  updated_at INTEGER DEFAULT (unixepoch())
);
```

##### 3.3.2 BAP 包含什么

| 配置类型 | 说明 | 示例 |
|----------|------|------|
| **关注指标 (KPI)** | 老板高频查看的指标及优先级 | `[{kpi: '毛利率', priority: 1}, {kpi: '库存周转', priority: 2}]` |
| **时间惯例 (Routine)** | 老板习惯的查看节奏 | `{daily_brief: '09:00', weekly_report: '周五 17:00', monthly_compare: '月初'}` |
| **预警阈值 (Alert)** | 老板设定的自动预警条件 | `{stock_low: 10, margin_drop: 5%, refund_rate_high: 8%}` |
| **关注领域 (Focus)** | 老板重点关注的产品/品类/客户/供应商 | `{products: ['A001','A003'], categories: ['手机配件'], suppliers: ['深圳XX']}` |
| **报告偏好 (Report)** | 老板偏好的报表格式和内容结构 | `{chart_first: true, include_comparison: true, detail_level: 'summary'}` |

##### 3.3.3 BAP 如何学习

秘书通过三种方式逐步构建老板画像：

**① 被动观察（Observed）**——核心学习方式
- 记录老板每次查询的关键词、模块、时间。
- 例如：老板最近 20 次查询中，14 次涉及「库存」和「毛利」→ BAP 自动将这两个指标置信度提升至 0.9。
- 例如：老板每周一早上习惯问「上周汇总」→ 秘书学会每周一自动推送周报。

**② 显式设置（Explicit）**——老板可手动配置
- 右键菜单新增「📊 关注设置」，打开 BAP 配置面板。
- 老板可手动设置：我想关注哪些指标、预警阈值多少、简报推送时间。

**③ 推理学习（Inferred）**——关联行为推断
- 例如：每次旺季（春节/双11）前，老板都频繁查库存 → 秘书在下一个旺季前提早 3 天预警。
- 例如：老板问完「销售额」后，80% 的概率会追问「退货率」→ 秘书默认将两者打包呈报。

##### 3.3.4 BAP 带来的体验变化

| 时间 | 阶段 | 秘书表现 |
|------|------|----------|
| 第 1 天 | 空白 | 通用欢迎语，万能但不精准 |
| 第 1 周 | 初步观察 | 开始记住老板常查的模块，快捷指令动态调整 |
| 第 1 月 | 画像成形 | 每日简报精确命中老板关注点，预警阈值自动校准 |
| 长期 | 深度默契 | 老板问一句她能补三句，关联推理主动呈报，成为真正的「懂老板的秘书」 |

##### 3.3.5 BAP 与 PCP 的关系（统一记忆层）

- **BAP（原秘书维护）**：记录「老板**关注什么数据**」——微观、高频、数据偏好。
- **PCP（项目上下文协议）**：记录「公司的**战略方向和约束**」——宏观、低频、决策框架。
- **CEO 偏好（决策学习）**：记录老板的预算敏感度、风险容忍、决策风格、自动确认阈值。
- **统一老板画像**：统一助理在回答问题时，综合 BAP + CEO 偏好 + PCP 活跃目标 + 决策统计，生成更贴合老板风格的建议。
- **交互**：统一助理可直接将老板口头目标写入 PCP（如「记录目标：下季度销售额翻倍」），无需再转交 CEO Agent。

#### 3.4 意图路由与决策确认

统一助理不再使用「碰壁话术」简单拒绝决策类请求，而是通过**意图路由**自动分类并处理：

##### 3.4.1 意图分类

| 意图类型 | 触发条件 | 处理方式 |
|---------|---------|---------|
| **query（查询）** | 数据/报表/功能类问题 | 直接走 commandParser / LLM 回答 |
| **decision（决策）** | 采购/定价/人事/营销/财务类关键词 | 生成决策建议卡片，写决策日志，弹窗确认 |
| **task（任务）** | 分派/派/安排/创建 +「任务」，或任务进度/列表查询 | 分派任务给子 Agent，或返回任务列表 |
| **context（上下文）** | 记录目标/愿景/里程碑/决策 | 写入 PCP（`project_context`） |
| **report（报告）** | 生成日报/周报/月报/经营报告 | 汇总数据生成报告 |

##### 3.4.2 决策确认流程

```
用户输入决策类请求
        │
        ▼
classifyAssistantIntent → decision
        │
        ▼
buildDecisionProposal（生成建议 + 风险/资金/工时评估）
        │
        ▼
submitDecisionProposal → 写入 ceo_decision_logs
        │
        ▼
FloatingAgentChat 弹出「决策确认」对话框
        │
        ▼
用户点击「确认执行」/「拒绝」
        │
        ▼
resolveDecision → 更新决策日志状态（approved / rejected + 反馈原因）
```

##### 3.4.3 决策确认卡片内容

| 字段 | 说明 |
|-----|------|
| 标题 | 决策确认 |
| 意图摘要 | 用户原始请求一句话 |
| 建议动作 | 对建议执行内容的描述 |
| 风险等级 | 🟢 低 / 🟡 中 / 🔴 高 |
| 资金影响 | 较小 / 中等 / 较大 |
| 操作按钮 | 确认执行 / 拒绝（可填写原因） |

> **设计原则**：不替老板决策，但主动提供专业建议；所有经营动作经确认后写入日志，确保可追溯。

### 10. 风险与备选

- **BAP 冷启动**：新用户无历史数据时，BAP 为空，秘书表现泛化。应对：提供预设模板（如「零售行业关注模板」「餐饮行业关注模板」），用户可在关注设置中一键套用，加速冷启动。
- **过度学习偏差**：如果老板某段时间集中关注某个问题（如临时盘点库存），BAP 可能过度拟合。应对：BAP 采用时间衰减权重，近 7 天数据权重更高，30 天前数据权重减半。同时老板可在面板中手动锁定/解锁偏好。
- **全系统只读的性能**：秘书的全局只读权限意味着每次查询可能跨多个数据表。应对：Rust 后端实现查询缓存 + 增量刷新；频繁查询的指标（库存总量、今日营收）每 5 分钟缓存一次。
- **合并后的职责认知**：用户可能不习惯秘书也能处理决策/任务。应对：统一助理在决策/任务前均弹窗确认，明确告知「这是经营决策，已为您生成建议，请确认」；保留决策日志供追溯，降低认知成本。
- **头像设计资源延迟**：若设计师未及时产出头像 SVG，初期使用 emoji 或不同颜色的 MUI Avatar 占位，头像选择器 UI 框架先行搭建。
- **语音功能依赖**：TTS/STT 能力依赖后续大模型接入和浏览器 Web Speech API，当前仅预留 UI 和类型结构。
