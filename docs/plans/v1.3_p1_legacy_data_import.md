# ProClaw v1.3 — 老系统数据迁移与导入适配 需求文档

> **版本**：v1.3 规划稿 v0.2（决策已敲定）
> **作者**：小如
> **日期**：2026-07-02
> **目标**：把用户旧版进销存系统导出的非标准 Excel（`.xls` / 带"基础信息"两行表头 / 多联系人重复）批量迁入桌面端 ProClaw
> **前置依赖**：v1.2 P1 批量导入中心（已完成）

---

## 一、背景与目标

### 1.1 背景

ProClaw v1.2 P1 已落地的「批量导入中心」覆盖了 **商品 / 库存 / 采购 / 销售 / 供应商 / 客户** 6 类业务对象，支持 CSV / JSON，XLSX 暂为 stub（提示用户另存为 CSV）。

但实际用户反馈：**绝大多数从旧系统导出的"经销存档案"是 `.xls` 格式，且表头不是单行字段名，而是"基础信息"标题行 + 字段名表头行的"两行表头"结构**。当前导入流程对此类数据无法直接使用，必须用户手动清洗（删标题行、改后缀、合并联系人），对中小商家门槛过高。

`D:\BigLionX\ProClaw\test-old-date` 目录下三个真实样例文件就是典型场景。

### 1.2 目标

让用户把以下特征的"旧经销存导出文件"一键迁入 ProClaw：

1. **格式**：`.xls`（OLE 二进制，Excel 97-2003）、`.xlsx`（OOXML）都直接解析，不再要求另存
2. **结构**：表头为"基础信息 / 联系信息"分段标题 + 字段名表头 的"两行表头"
3. **多联系人**：客户档案中"一个客户 + N 个联系人"的多行重复，自动聚合为一条客户记录 + 多条联系人
4. **自定义编码**：保留旧系统的自定义编码（`DL01 / DC001 / CNSHK0001 / V1XLJ1001` 等），不强制改写
5. **空类别自动建档**：商品 / 供应商 / 客户的"类别"列出现新值时，自动写入 `categories` 表
6. **数据规模**：单文件 1-3 万行（商品档案实测 22549 行）需稳定处理，不能 OOM

### 1.3 非目标（明确不做）

- ❌ 不做 OCR 识别扫描件 / PDF
- ❌ 不做企业 ERP（用友 / 金蝶 / SAP）标准接口
- ❌ 不做跨账套数据同步（仍是单用户本地导入）
- ❌ 不动 v1.2 P1 的 CSV / JSON 标准导入流程，老用户行为不变

## 三、现状缺口分析（v1.2 P1 的能力 vs 老数据需求）

| 缺口 | v1.2 P1 现状 | 老数据实际需要 | 影响 |
|------|------------|------------|------|
| **`.xls` 格式** | 完全不支持（只识别 csv/json/xlsx） | 供应商 / 客户都是 .xls | ❌ 用户必须先在 Excel 打开另存为 xlsx，多 1 步 |
| **`.xlsx` 真解析** | 是 stub，提示"另存为 CSV" | 商品导出 1 MB 真 xlsx | ❌ 大文件用户更不愿走 CSV 中转 |
| **两行表头识别** | 把 row0 "基础信息" 当作字段名 | row0 是分段标题，row1 才是字段名 | ❌ 字段映射全错位 |
| **分段标题**（基础信息 / 联系信息） | 无概念 | 客户表 row0 是合并单元格分段 | ❌ 无法告诉用户"以下列属于哪个段" |
| **多联系人聚合** | 一行一记录 | 客户表多行 = 一个客户 + N 联系人 | ❌ 导入会重复创建客户 |
| **自定义编码保留** | 不主动干预 | 用户旧编码（DL01 / CNSHK0001 等）有业务含义 | ⚠️ 当前会保留（用 code 字段 upsert），但没显式提示 |
| **类别自动建档** | categories 表存在但导入流程未触发 | 供应商类别 / 商品类别 出现新值 | ⚠️ 当前会原样存进 category 字符串，不建独立分类行 |
| **大类前缀识别**（HK / TW） | 不识别 | 客户编码前缀暗示地域 | ⚠️ 可选优化，可作为客户类型推断 |
| **超大数据** | executor 单行事务，2 万行 OK | 商品 22549 行 | ⚠️ 单事务可能长，但 SQLite 够用 |
| **V 系列编码（V1XLJ1001 重复）** | 按 SKU 严格 upsert，会去重失败 | 实际是 SPU/SKU 父子关系 | ❌ 会因唯一约束报错 |

## 四、解决方案总览

### 4.1 设计原则

- **不让用户清洗数据**：老格式直接吃进来，不要让用户在 Excel 里手动删标题行
- **复用 v1.2 P1 框架**：在现有 6 类导入流程上叠加"老格式适配层"，不重写
- **数据无损**：保留用户原编码，保留空值，绝不静默丢弃数据
- **失败明确**：解析 / 映射 / 校验 / 执行 四阶段每阶段都有清晰错误清单，用户能定位到行号

## 五、详细方案

### 5.1 数据格式原生解析（解决 `.xls` 与真 `.xlsx`）

#### 5.1.1 引入解析库

| 库 | 用途 | 体积 |
|----|------|------|
| `calamine = "0.30"` | `.xls`（OLE）+ `.xlsx`（OOXML）双格式解析 | 编译后 +1.8 MB（仅 Rust 二进制体积，不影响安装包） |
| `encoding_rs = "0.8"` | GBK / GB18030 解码（中文 xls 常用） | +0.3 MB |

**理由**：v1.2 P1 的"另存 CSV"提示对 2 万行商品表不友好；calamine 同时支持两种格式，是 Rust 生态的事实标准。

#### 5.1.2 路径实现

- 移除 `parser.rs` 的 `parse_xlsx_stub`
- 新增 `parser_legacy.rs`：
  - `detect_format(bytes) -> "xls" | "xlsx" | "csv" | "json"`：读文件头前 4 字节
    - `D0 CF 11 E0` → OLE2 → xls
    - `50 4B 03 04` → ZIP → xlsx
    - 其他 → 走 csv / json 旧逻辑
  - `parse_xls_xlsx(path) -> Vec<Vec<String>>`：calamine 入口，转为 UTF-8
- 修改 `commands.rs::import_create_batch` 接受 `source_path`（文件绝对路径），把文件读出来交给 calamine

#### 5.1.3 文件大小上限

- 单文件 ≤ 50 MB / ≤ 10 万行（硬限制，超出提示用户分批）
- 解析阶段 streaming，逐行返回，不一次性 load 全表

### 5.2 两行表头自动识别（解决"基础信息"标题行）

#### 5.2.1 表头探测算法

```rust
// src-tauri/src/import/header_detect.rs（新文件）
pub struct HeaderStructure {
    pub header_row_index: usize,  // 字段名所在行（0-based）
    pub segment_titles: Vec<(usize, usize, String)>, // (起始列, 结束列, 标题) — 合并单元格
    pub data_start_row: usize,    // 数据起始行
}

pub fn detect_header(rows: &[Vec<String>]) -> HeaderStructure {
    // 规则 1：扫描前 5 行，识别"合并单元格标题行"
    //   - 该行只有 1-2 个非空单元格，其余为空 → 视为分段标题
    //   - 例子：["基础信息", "", "", "", "", "", "", "", "联系信息", "", "", "", "", ""]
    
    // 规则 2：找字段名行
    //   - 含 * 前缀的列（如 "*供应商编号"）→ 强字段名
    //   - 出现在别名词典中的词 → 强字段名
    //   - 否则取规则 1 之后的下一行
    
    // 规则 3：数据起始行 = 字段名行 + 1
}
```

#### 5.2.2 案例实测预期

- 供应商 / 商品 / 客户 三份文件都能识别出：
  - header_row_index = 1（row1 是字段名行）
  - 客户文件 segment_titles = `[(0, 8, "基础信息"), (8, 14, "联系信息")]`
  - data_start_row = 2

### 5.3 多联系人聚合（解决客户档案多行重复）

#### 5.3.1 数据模型扩展

新增 2 张表（迁移文件 `database/migrations/061_legacy_import_extras.sql`）：

```sql
-- 客户多联系人
CREATE TABLE IF NOT EXISTS customer_contacts (
    id          TEXT PRIMARY KEY,
    customer_id TEXT NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
    contact_name TEXT NOT NULL,
    phone       TEXT,
    landline    TEXT,
    qq_wechat   TEXT,
    address     TEXT,
    is_primary  INTEGER DEFAULT 0,    -- 0/1，是否首要联系人
    source      TEXT DEFAULT 'manual',-- 'manual' / 'import' 区分来源
    created_at  TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_customer_contacts_customer ON customer_contacts(customer_id);

-- 商品 SPU/SKU 关系（已有 product_sku 表则跳过）
CREATE TABLE IF NOT EXISTS product_sku (
    id          TEXT PRIMARY KEY,
    product_id  TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    sku         TEXT NOT NULL UNIQUE,
    variant_name TEXT,                 -- 规格型号变体名
    spec        TEXT,                  -- 规格型号
    barcode     TEXT,
    source      TEXT DEFAULT 'manual',
    created_at  TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_product_sku_product ON product_sku(product_id);

-- 商品 / 供应商 / 客户 类别表
CREATE TABLE IF NOT EXISTS categories (
    id          TEXT PRIMARY KEY,
    type        TEXT NOT NULL,         -- 'product' / 'supplier' / 'customer'
    name        TEXT NOT NULL,
    parent_id   TEXT REFERENCES categories(id),
    source      TEXT DEFAULT 'manual', -- 'manual' / 'import_legacy'
    created_at  TEXT DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(type, name)
);
```

#### 5.3.2 聚合策略

**客户档案（C 客户表）**：
- 按 `客户编号` 分组 → 同一编号多行 → 1 条 customer + N 条 customer_contact
- 行级字段合并规则：
  - 基础信息列（客户名称 / 税号 / 银行 / 销售人员 / 客户等级）：取**首个非空值**
  - 联系信息列（联系人 / 手机 / 座机 / QQ/微信 / 联系地址）：每行变成一条 customer_contact
  - `首要联系人=是` 的行 → `is_primary=1`，其余 `=0`

**商品档案（B 商品表）**：
- 按 `商品编号` 分组 → 同一编号多行 → 1 条 product（取首个名称）+ N 条 product_sku
- 规格型号非空 → 作为 SKU 的 `spec` 字段
- 商品类别 → 自动写入 `categories(type='product', name=...)`

**供应商档案（A 供应商表）**：
- 按 `供应商编号` 分组（实测基本每行一供应商，无重复）→ 直接 1:1 upsert
- 供应商类别（去掉尾部 `/`） → 写入 `categories(type='supplier', name=...)`

### 5.4 字段映射扩展

## 十一、风险与限制

### 11.1 已知风险

| 风险 | 缓解措施 |
|------|---------|
| calamine 库对极旧 xls（Excel 95）兼容性 | 实测后如有问题，加 fallback：提示用户用 Excel 打开另存 xlsx |
| 22k 行单事务性能 | 改为 1000 行分块事务，每块独立 commit |
| 中文编码 GBK 误判 | encoding_rs 双重探测，先尝试 UTF-8 失败再 GBK |
| 多联系人 / SPU-SKU 聚合后用户想撤销 | Step 5 完成页提供"撤销本次导入"按钮（**不限时**，历史批次永久保留可回滚） |
| SPU/SKU 父子关系推断错误 | Step 4 强制让用户手动确认聚合规则：勾选 SPU 名 / 拆分 / 调整变体归属 |

### 11.2 不做的事

- ❌ 不导入库存 / 采购 / 销售单据（这三类业务单据需要日期 + 单据号，旧系统导出通常不完整）
- ❌ 不导入历史库存数量（防止凭空产生交易流水）
- ❌ 不导入图片附件（防止包体积爆炸）

### 11.3 与 ProClips 移动端协同

- 移动端不实现老格式导入（移动端场景下用户已经在 ProClaw 桌面端初始化过）
- 移动端读 customers / products / product_sku / customer_contacts 是 read-only，正常用即可
